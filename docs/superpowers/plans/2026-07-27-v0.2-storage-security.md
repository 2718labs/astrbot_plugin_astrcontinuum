# AstrContinuum v0.2.0 Storage Security Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v0.2.0 with authenticated encryption for every durable conversation-derived value, explicit locked behavior, safe provisioning and rotation, and content-free operator inspection.

**Architecture:** AES-256-GCM envelopes are owned by a small storage codec and bound to table, column, and primary key through length-prefixed AAD. Startup resolves key material before opening SQLite, then a storage-security coordinator atomically migrates or rekeys before constructing `SQLiteRepository`; failures leave the plugin locked while AstrBot continues natively. The request path only performs bounded in-process encrypt/decrypt calls backed by OpenSSL and SQLite C code; migration, rekey, WAL scrub, and `VACUUM` remain startup-only.

**Tech Stack:** Python 3.10+, `cryptography` AESGCM, SQLite WAL, Pydantic v2, AstrBot hooks and ADMIN commands, pytest, uv, Ruff, mypy.

## Task DAG

1. **S1 Crypto and key provisioning** — implement and verify the envelope, key sources, and offline helper.
2. **S2 Atomic storage activation** — add secure physical schema, legacy transform, verifier, rekey, and scrub.
3. **S3 Encrypted repository boundary** — require the codec and route every protected field through it without changing domain objects or CAS behavior.
4. **S4 AstrBot locked lifecycle and inspection** — compose startup safely and expose content-free ADMIN visibility.
5. **S5 v0.2.0 release closure** — align versions/dependencies/docs, run real gates, scan/package, and stop before remote push for user review.

Each task uses RED → verified RED → minimal GREEN → focused regression → commit. The current
wave and exact acceptance commands are recorded in the work-package index and task card.
