# AstrContinuum v0.2.0 Storage Security Design

Status: approved implementation direction

Date: 2026-07-27

Target: `astrbot_plugin_astrcontinuum` security-hardening release `v0.2.0`

## 1. Goal

AstrContinuum v0.2.0 protects durable conversation-derived payloads with authenticated
encryption before they reach SQLite, including WAL writes and online backups. The release
also provides an explicit locked state, plaintext-v0.1 upgrade, key rotation, recovery
instructions, and content-free operational inspection.

The security contract is:

```text
missing key, wrong key, unknown key id, invalid tag, or malformed envelope
=> AstrContinuum storage remains locked
=> no Journal, Snapshot, or compaction write occurs
=> native AstrBot conversation processing continues unchanged
=> logs and commands expose stable codes, never secrets or message content
```

The default key does not live in the AstrContinuum data directory. An operator must
provide a random 256-bit key through the process environment or a key file outside the
plugin data directory. A colocated automatically generated key is available only through
an explicit convenience mode and is reported as degraded protection.

This document narrows and supersedes the public-version and storage-security statements in
`2026-07-26-astrcontinuum-v1-design.md`. The earlier document's domain, provenance,
non-blocking, projection, fencing, and CAS invariants remain authoritative unless this
document explicitly changes their physical encrypted representation.

## 2. Threat Model

### 2.1 Protected scenarios

The design protects the confidentiality and integrity of conversation-derived durable
payloads when an attacker obtains:

- `astrcontinuum.sqlite3`;
- SQLite `-wal` and `-shm` companions;
- an online or offline database backup that does not include the external key;
- copied encrypted rows that are moved to a different protected field or record;
- a modified ciphertext, nonce, key id, or authentication tag.

An attacker with only these files must not recover session identity values, user or
assistant text, tool text, Capsule semantics, exact anchors, or rendered Snapshot context.

### 2.2 Visible metadata

Application-level encryption does not make the database indistinguishable from SQLite.
The following operational metadata remains visible:

- table and column names;
- row counts, event sequence numbers, timestamps, roles, event types, and token counts;
- job states, lease timing, retry codes, and coverage ranges;
- deterministic opaque ids and relationships between rows;
- the active non-secret key id and storage-format version.

This leakage is documented in README and SECURITY. Full-page SQLCipher encryption is not
used because AstrBot plugins must load across ordinary Windows, Linux, macOS, and container
Python environments without a platform-specific SQLite binary replacement.

### 2.3 Out of scope

v0.2.0 does not claim protection against:

- a hostile AstrBot process or another plugin running arbitrary code in that process;
- a compromised operating-system account that can read both the database and active key;
- plaintext already sent to the selected conversation or compaction Provider;
- plaintext retained in old user-created backups, filesystem snapshots, SSD remanence, swap,
  process dumps, or provider logs;
- recovery of a lost random key without a separately retained copy;
- FIPS certification or hardware-backed key custody.

Python cannot reliably zero every immutable key or plaintext copy held by the interpreter.
The implementation minimizes lifetime and avoids persistent/log copies without claiming
process-memory erasure.

## 3. Cryptographic Construction

### 3.1 Primitive

Protected values use `cryptography.hazmat.primitives.ciphers.aead.AESGCM` with:

- a 32-byte random key (AES-256);
- a fresh 12-byte random nonce for every encryption;
- the library's full 16-byte authentication tag;
- no nonce derivation, counter reuse, tag truncation, custom MAC, or custom padding.

`cryptography` is a direct runtime dependency because AstrContinuum imports it directly,
even when the target AstrBot installation already provides it transitively.

### 3.2 Envelope

Every encrypted scalar is stored as one versioned ASCII envelope:

```text
acenc:v1:<key-id>:<base64url-nonce>:<base64url-ciphertext-and-tag>
```

The parser is closed and bounded:

- exactly five colon-separated fields;
- literal prefix `acenc` and version `v1`;
- lowercase hexadecimal key id of fixed length;
- a decoded nonce of exactly 12 bytes;
- a decoded ciphertext containing at least the 16-byte tag;
- a configured maximum envelope and plaintext size;
- canonical unpadded base64url encoding.

The non-secret key id is the first 16 lowercase hexadecimal characters of
`SHA256(raw-key)`. Only uniformly random 32-byte keys are accepted, so the key id is not a
supported password-verification mechanism.

### 3.3 Associated data

Associated authenticated data binds a value to its physical authority:

```text
astrcontinuum | envelope-v1 | table | column | record-primary-key
```

The encoding uses length-prefixed UTF-8 fields rather than delimiter concatenation. Moving
an otherwise valid envelope between records, tables, or protected columns must fail tag
verification.

### 3.4 JSON-constrained columns

The v0.1 schema has SQLite `json_valid` and `json_type` checks. v0.2.0 preserves the table
and transaction structure while representing ciphertext in closed sentinel JSON:

```json
{"$astrcontinuum_encrypted": "acenc:v1:..."}
```

for object-constrained values, and:

```json
["$astrcontinuum_encrypted", "acenc:v1:..."]
```

for array-constrained values.

The repository accepts these shapes only when storage security is active. Domain models
continue to receive the original canonical JSON after authenticated decryption. Plaintext
JSON is accepted only inside the dedicated legacy migration transaction.

## 4. Protected Data Inventory

The following physical values are encrypted:

| Table | Protected values |
| --- | --- |
| `sessions` | canonical SessionKey JSON and every denormalized identity component |
| `journal_events` | complete `content` |
| `capsules` | complete canonical Capsule JSON, including exact quotes and source-linked semantics |
| `snapshots` | exact-anchor id array, rendered context, and audit outcome |
| `storage_security` | fixed key verifier |

Nullable identity components remain SQL `NULL`; nullness is operational metadata. Event
type, role, source Hook, sequence, token count, coverage, lifecycle state, lease state,
and already-redacted error tuples remain plaintext so existing constraints and bounded
administration continue to function.

`idempotency_key`, deterministic row ids, and `session_key_hash` remain lookup metadata in
v0.2.0. They must never contain raw message text. Their equality and correlation leakage is
part of the documented metadata boundary.

All repository construction requires an explicit secure codec. There is no implicit
plaintext production codec and no configuration switch that permits new plaintext writes.
Tests may use a named test-only deterministic key fixture, not a production fallback.

## 5. Key Sources

### 5.1 External environment source (default)

`encryption_key_source = "environment"` reads:

```text
ASTRCONTINUUM_MASTER_KEY
ASTRCONTINUUM_PREVIOUS_KEY
```

The active variable is required and contains one unpadded base64url-encoded 32-byte random
key. The optional previous variable is accepted only during one rotation or recovery. Empty,
malformed, short, long, or identical active/previous values lock storage.

Environment mode is intended for an orchestrator or secret manager that injects the value at
process start. The key must not be hardcoded in a container image, compose file, service file,
shell profile, repository, or CI log.

### 5.2 External file source

`encryption_key_source = "file"` reads the active path from `encryption_key_file` and an
optional old-key path from `encryption_previous_key_file`. Each file contains only the same
base64url key plus an optional final newline.

The active path must resolve outside AstrContinuum's plugin data directory. Symlinks and
relative traversal are resolved before the boundary check. The plugin reads a bounded file,
rejects non-regular files, and never writes or changes the supplied file.

External file mode is the recommended manual-installation path. Docker, Kubernetes, and
systemd deployments should prefer a read-only secret-mounted file supplied by their secret
manager. Both active and previous key paths must satisfy the same
outside-data-directory boundary.

### 5.3 Explicit local convenience source

`encryption_key_source = "local"` creates `astrcontinuum.key` with exclusive creation and
restrictive permissions inside the plugin data directory. Existing files are never
overwritten. This mode:

- still encrypts every protected database value;
- protects a database or backup copied without the key file;
- does not protect a copied whole plugin data directory;
- is displayed as `LOCAL_KEY_DEGRADED` in status and documentation;
- is never selected implicitly after an external-key error.

The default remains `environment`.

### 5.4 Administrator provisioning

The encryption key belongs to one AstrContinuum installation, not to an individual chat
administrator. Two roles are deliberately separated:

- a chat administrator may run ADMIN-only status and provenance commands but cannot retrieve,
  submit, replace, export, or reveal key material through AstrBot;
- a host/deployment administrator controls the process environment, external secret file, or
  secret manager and is the only role that provisions the key.

AstrContinuum includes an offline helper:

```text
python -m astrcontinuum.keyctl generate --output <external-key-file>
python -m astrcontinuum.keyctl fingerprint --key-file <external-key-file>
```

`generate` creates a new 32-byte random key with exclusive file creation. The output path must
not already exist and must resolve outside the plugin data directory when that directory is
provided for validation. The helper attempts restrictive owner-only permissions and reports
when the operating system cannot prove them. It prints only the non-secret key id and
destination path; it does not print the raw key by default.

`fingerprint` validates an existing key file and prints only its non-secret key id. Neither
command accepts raw key material as a command-line argument, because process listings and
shell history are not secret channels.

For an automated deployment, the administrator should generate and retain the key inside the
organization's secret manager, then expose it to AstrBot as an injected environment variable
or read-only mounted file. AstrContinuum does not email, message, display, download, or
otherwise "send" a master key to an administrator.

At least one separately protected recovery copy is required before production use. Access to
that copy follows the operator's least-privilege and audit policy. `/context_status` exposes
the short key id so the administrator can confirm which secret is active without revealing
it.

### 5.5 Key handling

Keys never appear in configuration JSON, SQLite, logs, exceptions, command replies, hashes
other than the non-secret short key id, package files, test artifacts, or diagnostics.
Public exceptions carry only stable codes. Internal exception chaining at the key boundary is
suppressed when it could include a path or malformed secret.

## 6. Storage State and Startup

A singleton `storage_security` table records:

```text
format_version
active_key_id
state = NEEDS_MIGRATION | NEEDS_REKEY | NEEDS_SCRUB | ACTIVE
key_verifier
created_at
updated_at
```

The verifier is an encrypted fixed random-independent constant bound to the singleton row.
It proves that a supplied key can authenticate storage without decrypting conversation data.

Plugin initialization proceeds in this order:

1. parse security configuration without opening SQLite;
2. resolve and validate active and optional previous key material;
3. open SQLite and apply structural migrations;
4. read or create `storage_security`;
5. authenticate the key verifier;
6. migrate or rekey before constructing the repository;
7. complete required WAL/plaintext-remnant scrub;
8. construct the encrypted repository and start the compaction worker;
9. report `ACTIVE` or `LOCAL_KEY_DEGRADED`.

If any step before repository construction fails, AstrContinuum enters a request-safe locked
state. Hooks perform no AstrContinuum persistence or projection, and native AstrBot behavior
continues. `/context_status` remains available and reports a stable remediation code.

## 7. Plaintext v0.1 Upgrade

### 7.1 Detection and preflight

An existing schema without `storage_security` is a legacy candidate. Before changing rows,
the upgrader:

- verifies the complete migration ledger and foreign keys;
- verifies every legacy JSON value against its domain model;
- checks row counts and authoritative relationships;
- rejects any value already resembling a malformed encryption sentinel;
- requires a valid active key;
- acquires an exclusive bounded migration transaction before the worker exists.

No plaintext backup is created automatically. Operators who require rollback must stop
AstrBot and make a protected offline backup before installing v0.2.0.

### 7.2 Atomic transform

Inside one transaction, the upgrader encrypts every protected value, inserts the verifier,
records `NEEDS_SCRUB`, and re-reads/decrypts every transformed row to prove wire equality.
Any failure rolls back the complete transform. The plugin remains locked and the original
legacy rows remain readable by v0.1, but v0.2 performs no new write.

After commit, startup runs:

```text
PRAGMA wal_checkpoint(TRUNCATE)
PRAGMA secure_delete = ON
VACUUM
PRAGMA wal_checkpoint(TRUNCATE)
```

and only then records `ACTIVE`. If the process stops after transform commit but before the
scrub marker, the next startup repeats the idempotent scrub. This removes ordinary SQLite
free-page and WAL copies but does not claim forensic erasure from SSDs, filesystem snapshots,
swap, or old backups.

## 8. Rotation and Recovery

When the database verifier key id differs from the configured active key:

1. the previous key must match and authenticate the current verifier;
2. the active key must be distinct and valid;
3. one exclusive transaction decrypts with the previous key and encrypts every protected
   value with the active key;
4. the transaction decrypts every new envelope and proves exact wire equality;
5. the verifier and active key id change atomically with all protected rows;
6. post-commit scrub runs before status becomes `ACTIVE`.

If the previous key is absent or wrong, state is locked with `STORAGE_PREVIOUS_KEY_REQUIRED`;
no row is partially rotated. After successful rotation, status instructs the operator to
remove the previous-key setting while retaining a protected recovery copy according to their
backup policy.

The operator workflow is:

1. keep AstrBot stopped or the plugin disabled while changing secret configuration;
2. generate a new key in the external secret manager or with offline `keyctl`;
3. configure the new key as active and the current key as previous;
4. start or reload the plugin;
5. wait for `/context_status` to report `ACTIVE`, the new key id, and no rekey/scrub work;
6. make and restore-test an encrypted database backup paired with the new recovery key;
7. remove the previous-key setting and reload once more;
8. retain or destroy the retired key according to the backup-retention policy.

Rotation never requires either raw key to pass through a chat command or WebUI text field.
If any preflight, re-encryption, verification, commit, or scrub step fails, the transaction
does not partially rotate rows. The operator restores the old key as active and investigates
the stable status code.

Local convenience mode rotates by leaving local mode: copy the old local key into a protected
external recovery location, generate a new external key, select external file or environment
mode, and supply the old key as previous for the one-time transaction. The plugin never
silently overwrites `astrcontinuum.key`.

Recovery is key restoration, not cryptographic bypass. Restoring the matching active key
unlocks the database. A lost random key makes the encrypted payload unrecoverable; no support
command or hidden fallback can reconstruct it.

## 9. Repository Boundary and Runtime Behavior

`astrcontinuum/storage/crypto.py` owns envelopes, key parsing, AAD, and content-free crypto
errors. `astrcontinuum/storage/security.py` owns key-source resolution, security metadata,
migration, rekey, and scrub orchestration. `SQLiteRepository` owns domain serialization and
calls the codec immediately before SQL parameters and immediately after rows are read.

Encryption changes only physical representation:

- domain envelopes, deterministic ids, source coverage, and CAS semantics remain unchanged;
- Journal append-only and Capsule/Snapshot logical immutability remain unchanged;
- rekey may update physical ciphertext while proving the decrypted wire payload is identical;
- live hooks never call a remote service for encryption or key resolution;
- compaction and request views operate on decrypted in-memory domain objects;
- no decrypted payload is cached globally or written to temporary files.

AES-GCM work remains bounded by existing payload limits. Migration, rekey, and VACUUM occur
only during initialization before the worker starts, never on the live Hook path.

## 10. Operator Visibility

`/context_status` remains ADMIN-only and adds:

```text
数据保护：ACTIVE | LOCAL_KEY_DEGRADED | LOCKED
加密格式：AES-256-GCM / envelope-v1
密钥来源：environment | external file | local convenience
活动密钥标识：<short non-secret key id>
存储维护：ACTIVE | NEEDS_MIGRATION | NEEDS_REKEY | NEEDS_SCRUB
安全代码：<stable code or NONE>
```

When locked, event, Snapshot, and job counts are not queried because the repository is not
available.

A new ADMIN-only `/context_inspect` command reports only current-session provenance:

- active Snapshot id suffix and pointer version;
- covered range, Journal high-water mark, and Delta range;
- counts by event type and Capsule slot;
- pending job state and retry code;
- active degradation and security codes.

It never returns message text, exact anchors, Capsule semantic text, raw SessionKey values,
Provider ids, key paths, key material, ciphertext, object `repr`, or exception text.

Mutating administration commands such as data deletion, pointer rollback, or accepting keys
through chat are deliberately excluded from v0.2.0. Existing durable worker retry and lease
recovery remain automatic. This keeps the security release free of a new destructive command
surface.

## 11. Configuration

The configuration schema adds, without removing existing keys:

| Key | Type | Default | Meaning |
| --- | --- | --- | --- |
| `encryption_key_source` | string choice | `environment` | `environment`, `file`, or explicit `local` |
| `encryption_key_file` | file | empty | active external key file for `file` mode |
| `encryption_previous_key_file` | file | empty | one old external key file during rotation |

Descriptions explain:

- where to set the two environment variables;
- how to use offline `keyctl` for manual external-file provisioning;
- why secrets must not be pasted into AstrBot configuration or chat;
- that the default locks until an external key exists;
- that local mode has a weaker whole-directory threat boundary;
- that a v0.1 database is transformed on the first successful keyed startup.

Invalid values never fall back to another source.

## 12. Versioning and Compatibility

The release updates:

- `metadata.yaml` to `v0.2.0`;
- `pyproject.toml` to `0.2.0`;
- the AstrBot registration version to `0.2.0`;
- `CHANGELOG.md`, README, SECURITY, architecture, database, migration, and roadmap documents;
- `requirements.txt` and `uv.lock` with the direct `cryptography` dependency.

The SQLite migration is forward-only. v0.1 cannot read an encrypted v0.2 database. The
upgrade guide therefore requires a stopped, protected backup before installation when an
operator needs software rollback.

No new AstrBot private API is introduced. The compatibility floor remains the currently
verified `>=4.24.0,<5.0.0` unless the real load matrix proves otherwise. Empty
`support_platforms` remains preferable to claiming an untested adapter.

## 13. Error Model

Stable public codes include:

```text
STORAGE_KEY_MISSING
STORAGE_KEY_INVALID
STORAGE_KEY_FILE_UNSAFE
STORAGE_LOCAL_KEY_CREATE_FAILED
STORAGE_KEY_MISMATCH
STORAGE_PREVIOUS_KEY_REQUIRED
STORAGE_ENVELOPE_INVALID
STORAGE_AUTHENTICATION_FAILED
STORAGE_LEGACY_VALIDATION_FAILED
STORAGE_MIGRATION_FAILED
STORAGE_REKEY_FAILED
STORAGE_SCRUB_FAILED
```

Codes contain no dynamic suffix. Logs may include the stage, code, affected-row count, and
whether local convenience mode is active. They may not include key paths, row content,
SessionKey components, ciphertext, nonce, tag, raw database exceptions that echo values, or
host object representations.

Authentication failure is never treated as an empty message, absent Snapshot, or retryable
compaction error. It locks the storage boundary so corrupted or attacker-modified data cannot
silently enter model context.

## 14. Verification

### 14.1 Unit tests

- key parser accepts exactly one canonical 32-byte encoding;
- nonce uniqueness across repeated encryption of the same value;
- exact round trip for UTF-8, Chinese, empty text, and maximum bounded payloads;
- wrong key, wrong AAD, cross-row swap, cross-column swap, modified tag, malformed envelope,
  unknown version, and unknown key id all fail with content-free codes;
- JSON object and array sentinels are closed and cannot collide with valid domain payloads;
- external file boundary and symlink resolution reject unsafe paths;
- local mode never overwrites an existing key file;
- `keyctl` never overwrites a file, prints raw key material, or accepts it in process arguments;
- generated and fingerprinted key ids match runtime status without revealing the key.

### 14.2 SQLite integration tests

- a fresh database contains no synthetic identity, message, Capsule, anchor, or Snapshot
  plaintext in the main file or truncated WAL;
- repository reads reconstruct byte-for-byte equivalent domain envelopes;
- all idempotency, sequence, lease, fencing, CAS, and publication tests pass through encryption;
- legacy fixture migration preserves every wire object and row relationship;
- injected pre-commit failure leaves the entire legacy database unchanged;
- injected post-commit/pre-scrub stop resumes scrub idempotently;
- rotation is atomic and the old key cannot authenticate new envelopes;
- missing previous key locks without changing any row;
- corrupted ciphertext never reaches assembler or compiler input.

### 14.3 AstrBot and release tests

- missing external key loads the plugin in clear locked status and leaves native requests alone;
- correct external key initializes, captures, compacts, reloads, and restores normally;
- local mode is visibly degraded;
- disable, enable, reload, and terminate release every worker and SQLite resource;
- `/context_status` and `/context_inspect` contain no fixture secrets;
- clean AstrBot `4.24.x` and `4.26.7` load probes pass where dependencies are installable;
- DevKit validation reports zero errors;
- Ruff, mypy, pytest, migration checks, and archive plaintext scans pass;
- the final whitelist archive is below the AstrBot market limit and contains no key, database,
  WAL, cache, test data, or virtual environment.

## 15. Release Gate

v0.2.0 is ready to push only when all of the following are evidenced on the exact packaged
source:

1. every protected-field test and legacy migration/rotation crash test passes;
2. a raw-file scan cannot find the known synthetic secrets after checkpoint and scrub;
3. wrong or missing keys demonstrate locked, no-write behavior on real AstrBot;
4. correct-key real AstrBot lifecycle and background compaction pass;
5. version strings, CHANGELOG, requirements, lock file, and documentation agree;
6. the extracted archive passes the AstrBot validator with zero errors;
7. no key or secret-bearing test artifact is staged or packaged;
8. the user reviews the final diff and explicitly authorizes the remote push.
