# AstrContinuum v0.2.1 Tokenizer 与自动上下文窗口设计

状态：设计已确认，进入 v0.2.1 实现计划

日期：2026-07-28

目标版本：`astrbot_plugin_astrcontinuum` `v0.2.1`

发布基线：已发布的 `v0.2.0`

## 1. 目标

AstrContinuum v0.2.1 用真正的本地 tokenizer 取代“一个 UTF-8 字节等于一个
Token”的在线预算近似，同时保持现有 Journal 不可变、后台归约与实时请求分离、
存储加密和请求失败开放等约束。

本版本是 `v0.2.0` 架构重构后的补丁增强，不重新定义已发布的 v0.2 协议。

本设计必须同时解决：

- 中文、Emoji、代码和中英混排被 UTF-8 字节计数严重高估；
- OpenAI、MiniMax、Claude 等模型并不共享同一 tokenizer；
- 用户可以在同一会话中切换模型；
- 后台归约模型可以不同于实时对话模型；
- 已持久化的 `token_count` 已参与幂等校验与对象标识，不能原地改写；
- AstrBot 能提供模型窗口元数据，但插件不能依赖未公开的 tokenizer API；
- tokenizer 不能增加远程文本传输、事件循环阻塞或静默单位混用。

发布契约为：

```text
持久化指标使用稳定的规范坐标系
实时预算使用本次请求的模型坐标系
后台归约请求使用归约模型坐标系
一次预算计算只能使用一个 tokenizer profile
任何最终投影都必须经过完整重新计数
tokenizer 或元数据故障不得阻断 AstrBot 原生聊天
```

## 2. 范围与非目标

### 2.1 v0.2.1 范围

- 增加本地 `tiktoken` 依赖和离线编码资源；
- 增加不可变 tokenizer profile、注册表和请求级路由器；
- 将 `model_context_limit = 0` 定义为自动跟随当前模型；
- 将持久化规范计量、实时请求计量和后台归约计量分轨；
- 将现有明文兼容计数字段迁移为逻辑等价的加密 envelope；
- 增加加密的派生 Token metric sidecar；
- 渐进补齐旧 Journal、Snapshot 和 Capsule 的规范 metric；
- 改造实时预算装配，避免对增长中的完整前缀重复编码；
- 在管理员状态中显示实际模型窗口、计数模式和降级状态；
- 增加 Python 3.10、3.11、3.12、3.13 及 Windows 3.12 验证。

### 2.2 非目标

- 不声称能精确复刻未公开的 MiniMax 或 Claude tokenizer；
- 不调用远程 tokenizer、第三方计数 API 或 Provider 私有端点；
- 不根据 Provider usage 自动训练或长期校准倍率；
- 不精确复刻每家 Provider 的 Chat Template、多模态计费和工具 Schema 计费；
- 不重写 AstrBot 保存的对话历史；
- 不原地修改已有 Journal、Snapshot、Capsule 或其确定性 ID；
- 不向普通管理员暴露 tokenizer 名称、词表路径或安全倍率配置项；
- 不引入 Hugging Face `transformers`、远程模型仓库或运行时词表下载。

## 3. 已确认的设计决策

### 3.1 路由策略

采用混合 tokenizer 路由：

- `tiktoken` 能明确识别且本地资源可用的 OpenAI 模型，使用对应文本编码；
- MiniMax、Claude 和其他未知或闭源模型，使用 `o200k_base` 多语言参考编码；
- 参考编码的请求计数应用固定 10% 安全余量；
- 任一解析、加载或计数失败时，该次完整预算重新使用 `utf8-byte-v1`；
- Provider 为 OpenAI 兼容接口不代表其模型是 OpenAI 模型，禁止按接口类型猜测；
- 模型名称只允许通过 `tiktoken` 的已知映射或显式封闭映射表命中，禁止子串模糊匹配。

这里的“精确”仅指已知 OpenAI 模型的文本 BPE 编码。Provider 的消息边界、角色标记、
工具 Schema、多模态内容和服务端附加提示仍由固定安全预留覆盖。

### 3.2 自动模型窗口

配置语义固定为：

```text
model_context_limit > 0  => 管理员手动覆盖
model_context_limit = 0  => 自动读取当前会话模型窗口
model_context_limit < 0  => 无效配置，使用安全兜底并报告稳定代码
```

只有 `model_context_limit` 支持自动模式。`target_input_budget` 和
`hard_input_ceiling` 继续作为显式安全阀，不随模型切换自动变化。

### 3.3 三轨计量

系统使用三个互不混用的计量轨道：

1. 持久化规范轨道：固定 `canonical-o200k-v1`；
2. 实时请求轨道：按当前对话模型解析的 request profile；
3. 后台归约轨道：按归约 Provider 模型解析的 compaction profile。

每条轨道都返回不可变 profile。不存在可变的插件级“当前 tokenizer”单例。

## 4. Tokenizer Profile

逻辑 profile 包含：

```text
profile_id
schema_version
mode = CANONICAL | EXACT_TEXT | REFERENCE | BYTE_FALLBACK
encoding_name
implementation_name
implementation_version
asset_digest
count_multiplier_basis_points
```

固定 profile 为：

| Profile | 用途 | 原始编码 | 倍率 |
| --- | --- | --- | --- |
| `canonical-o200k-v1` | 持久化派生指标 | `o200k_base` | 10000 |
| `openai-<encoding>-v1` | 已知 OpenAI 请求 | 模型映射编码 | 10000 |
| `reference-o200k-v1` | MiniMax、Claude、未知模型 | `o200k_base` | 11000 |
| `utf8-byte-v1` | 完整请求故障回退 | UTF-8 字节长度 | 10000 |

倍率采用整数基点，避免平台浮点差异：

```math
T_p(x) =
\left\lceil
\frac{m_p \cdot T_{\mathrm{raw},p}(x)}{10000}
\right\rceil .
```

其中规范轨道不使用安全放大；10% 放大只属于未知模型的请求或归约调用预算。

Profile ID 是存储和状态中的稳定协议值。依赖库升级不能悄悄改变已有 profile 的
语义；若官方词表或编码规则发生变化，必须增加新的 schema/profile 版本并单独设计
迁移。

所有普通消息、工具 JSON 和 Capsule 文本都使用 ordinary-text 编码语义。用户输入中
即使出现 `<|endoftext|>` 等特殊 token 字面量，也按普通文本计数，不触发特殊 token
解析或异常。

## 5. 组件边界

### 5.1 `TokenizerRegistry`

职责：

- 从插件只读资源加载允许的编码资产；
- 验证资产 SHA-256；
- 构造并缓存线程安全的 `tiktoken.Encoding`；
- 提供规范、精确文本、参考和字节回退 counter；
- 只返回稳定、无内容的错误代码。

它不解析 AstrBot Provider，不读取配置，不访问 SQLite，也不联网。

### 5.2 `TokenizerRouter`

职责：

- 接收已清洗的 request model identity；
- 调用 `tiktoken` 模型映射确定编码名称；
- 只接受本地白名单编码；
- 未知模型返回 `reference-o200k-v1`；
- 任何异常返回显式的 BYTE_FALLBACK 决策。

它不缓存对话内容，也不持有“当前模型”状态。

### 5.3 `ContextLimitResolver`

职责：

- 优先应用正数手动配置；
- 自动模式下读取当前 AstrBot Provider 已解析的 `max_context_tokens`；
- 识别请求级模型覆盖与 Provider 默认模型不一致的情况；
- 缺失、无效或无法证明匹配时使用安全兜底；
- 返回数值和无内容来源标签。

返回来源仅允许：

```text
MANUAL
AUTO_ASTRBOT
AUTO_SAFE_FALLBACK
```

### 5.4 `RequestBudgetProfile`

每次 `on_llm_request` 创建一个不可变请求对象，包含：

```text
normalized model identity
context limit and source
tokenizer profile
target input budget
hard input ceiling
reserved output/tools budget
fixed safety margin
```

它被同一次请求的压力判断、候选装配、最终复核和状态记录共同使用。

### 5.5 `TokenMetricStore`

职责：

- 保存 artifact 在指定 profile 下的派生计数；
- 通过现有存储加密边界保护 metric payload；
- 使用 CAS 保证同一 artifact/profile 的计数确定；
- 为旧 artifact 提供有界、幂等的后台补齐；
- 不成为第二份对话内容存储。

## 6. 模型身份与上下文窗口解析

### 6.1 模型身份

解析顺序为：

1. 非空且格式有效的 `ProviderRequest.model`；
2. `Context.get_using_provider(umo)` 返回 Provider 的 `get_model()`；
3. 未知模型标识。

Provider ID 和适配器类型不参与 tokenizer 精确映射。模型标识只保存在请求内存中，
状态和日志只显示 profile 与来源标签，不显示 Provider ID 或原始模型字符串。

### 6.2 自动窗口

当前 AstrBot 会在 `OnLLMRequest` 插件钩子之前，根据模型元数据或 AstrBot 自身兜底
填充 Provider 的 `provider_config["max_context_tokens"]`。AstrContinuum 只读取该
已解析值，不导入 `astrbot.core.*`，也不再次请求 models.dev。

自动解析规则为：

1. Provider 字段是正整数且请求没有不匹配的模型覆盖：使用该值；
2. 请求模型覆盖与 Provider 默认模型不同：使用
   `min(valid_provider_limit, 128000)`；
3. Provider、字段或 API 不可用：使用 `128000`；
4. 解析结果不大于输出/工具预留：不构造受控投影，保留原生请求。

请求之后发生的 Provider 失败切换属于 AstrBot 调度边界，插件在预请求钩子中无法
权威预知。AstrContinuum 因此不声称覆盖该 Provider 的精确窗口；AstrBot 自身的
Provider 限制仍是最终保护。

### 6.3 有效输入预算

对一次已解析请求：

```math
B_{\mathrm{input}}
=
\min
\left(
B_{\mathrm{target}},
B_{\mathrm{hard}},
C_{\mathrm{model}} - R_{\mathrm{output/tools}}
\right).
```

其中默认 `R_output/tools = 32000`，现有固定 `safety_margin = 2000` 保持不变。
目标预算和硬上限即使大于自动窗口也不会导致越界，因为最终预算取最小值。

## 7. 离线资源与依赖

`pyproject.toml` 和 `requirements.txt` 增加：

```text
tiktoken>=0.12,<0.14
```

`uv.lock` 锁定实际解析版本。插件发布包不包含第三方 wheel、虚拟环境或编译产物。

官方 `tiktoken` 编码构造默认可能从 OpenAI 公共存储加载 `.tiktoken` 排名文件。
AstrContinuum 不允许运行时下载，因此随插件只读资源提供：

```text
o200k_base.tiktoken
cl100k_base.tiktoken
```

`o200k_harmony` 复用 `o200k_base` 的 mergeable ranks；普通文本计数不需要增加第三份
排名资源。每份资源在加载前匹配固定官方 SHA-256。资产校验失败不会尝试联网修复。

发布包保留上游许可与归属说明。精确包体由发布流水线从白名单源文件构建并验证：

```text
archive size < 16 MiB
no wheel
no .venv
no tokenizer cache
no database/WAL/key
```

## 8. 持久化规范指标

### 8.1 现有逻辑字段保持不可变

已有 Journal `token_count`、Snapshot/Capsule `token_cost` 已参与幂等比较、验证或
确定性 ID。v0.2.1 不修改这些字段解密后的逻辑值，也不改变旧对象 ID。

包括 v0.2.1 新对象在内，现有字段固定继续使用 `utf8-byte-v1`，仅承担 wire
兼容、幂等和旧验证职责，不再被解释为当前模型的真实 token 数。实时模型预算和新
规范分段都不得直接使用这些兼容字段。Segmenter 只使用
`canonical-o200k-v1` sidecar；sidecar 缺失时延迟该会话的归约，而不是回读兼容字段
混算。

“不修改”指解密后的领域值、对象身份和关系不变，不代表继续以明文 INTEGER 保存。
当前 SQLite schema 的兼容计数列会在一次有界的启动期结构迁移中转为 AES-GCM
envelope：

1. 获取独占迁移事务；
2. 为每个旧整数生成绑定原表、原列和 artifact ID 的加密 envelope；
3. 重建受影响表并保留全部主键、外键、唯一约束和顺序；
4. 逐行解密并证明逻辑整数与迁移前完全一致；
5. 提交后执行现有 WAL checkpoint、secure-delete 和 VACUUM scrub；
6. scrub 完成后才允许 AstrContinuum 存储进入 ACTIVE。

任一步骤失败会回滚结构迁移或保持现有 `NEEDS_SCRUB` 恢复语义。插件存储保持锁定，
不进行 Journal、metric 或归约写入；AstrBot 原生聊天继续。Repository 在领域边界
仍读写普通非负整数，因此 EventEnvelope、幂等比较和 Snapshot/Capsule ID 语义不变。

### 8.2 Sidecar 逻辑结构

逻辑 metric 为：

```text
artifact_kind = EVENT | SNAPSHOT | CAPSULE
artifact_id
tokenizer_profile_id
token_count
```

物理 SQLite 结构只明文保存 artifact/profile 标识和加密 envelope：

```text
artifact_kind
artifact_id
tokenizer_profile_id
metric_envelope
created_at
PRIMARY KEY (artifact_kind, artifact_id, tokenizer_profile_id)
```

`metric_envelope` 使用现有 AES-256-GCM codec。AAD 绑定表名、artifact kind、artifact
ID、profile ID 和 envelope 版本。精确计数不以明文整数列保存。

规范 metric 的计数文本固定为：

| Artifact | 规范计数文本 |
| --- | --- |
| Event | adapter 已验证并用于候选渲染的内容文本；结构化工具内容使用确定性 canonical JSON |
| Capsule | Capsule 的完整规范渲染块 |
| Snapshot | 完整 `rendered_context` |

Canonical JSON 固定 UTF-8、排序键、无非语义空白和稳定分隔符。规范轨道不加入
Provider role、Chat Template 或工具调用框架，因为它只服务持久化分段和派生对象
验证，不代表任一 Provider 的请求成本。

### 8.3 新 artifact 写入

正常情况下，权威 artifact 与 `canonical-o200k-v1` metric 在同一 SQLite 事务中
提交。规范文本和计数在打开写事务之前完成，事务内部只执行有界的加密与 SQL 写入，
不在 SQLite 写锁内加载词表或运行大段 tokenizer 工作。

同一事务还会把兼容 `utf8-byte-v1` 计数写入 artifact 自身的加密 count envelope。

若规范 tokenizer 不可用：

- 权威 Journal 写入仍可按现有兼容计数完成；
- 同一事务登记无内容的 metric-backfill intent；
- 该会话的后台归约等待 canonical metric；
- 实时聊天继续使用本次请求的 BYTE_FALLBACK profile。

派生 metric 故障不能使已经合法捕获的权威事件消失。

### 8.4 旧数据渐进补齐

旧 artifact 的 canonical metric 不写回权威对象。后台归约通道按会话、有界批次
写入 sidecar：

1. 读取并认证加密 artifact；
2. 在内存中提取需要计数的规范文本；
3. 使用 `canonical-o200k-v1` 计数；
4. 加密 metric payload；
5. CAS 插入 sidecar；
6. 验证同一 artifact/profile 的已有值完全一致。

补齐操作幂等、可中断、可在重启后继续。密钥不可用、认证失败或资产损坏时停止该
会话的补齐和归约，存储状态按现有安全设计保持锁定或降级；实时原生聊天不等待它。

## 9. 实时请求数据流

完整顺序为：

```text
OnLLMRequest
→ 解析 Provider / model / context limit
→ 路由不可变 request tokenizer profile
→ 捕获本轮权威事件与 canonical metric
→ 构造同一高水位 RequestView
→ 一次 asyncio.to_thread() 执行完整预算装配
→ 批量计数候选块
→ 确定性选择并渲染 AC 投影
→ 对最终完整 AC 投影重新计数
→ 超限则移除最低优先级可选组并重新复核
→ 通过预算与既有图证书后才写回 ProviderRequest
```

所有 profile 解析在进入线程任务前完成。线程任务不调用 AstrBot API、SQLite 或网络。
请求内计数缓存只以 `(block_id, profile_id)` 为键，随请求释放，不保存明文全局缓存。

### 9.1 Provider usage 的角色

`Conversation.token_usage` 是上一轮 Provider 返回的滞后观测，可能为零，且不是当前
请求 token 数。它可以继续作为提前启动归约的压力信号，但：

- 不选择 tokenizer；
- 不替代当前请求完整计数；
- 不证明最终投影满足当前模型窗口。

最终预算始终由本次 `RequestBudgetProfile` 复核。

## 10. 后台归约数据流

后台 Worker 解析独立 compaction profile：

- 留空 `compaction_provider_id` 时跟随当前对话模型；
- 指定 MiniMax 等模型时使用其模型 identity；
- 已知编码使用精确文本 profile；
- 未知模型使用 `reference-o200k-v1`；
- 失败时使用整次 BYTE_FALLBACK，并缩小输入而不是混合单位。

Worker 在调用归约 Provider 前，用 compaction profile 对最终序列化请求重新计数。
模型输出继续受现有闭合 Schema、事件编号、逐字引文、speaker ownership 和机械验证
约束；tokenizer 不放宽 extractive-only 边界。

归约生成的 Snapshot/Capsule 回到持久化轨道，以 `canonical-o200k-v1` 写入 sidecar。
未来发送给实时模型时，再用实时 request profile 重新计数其渲染文本。

## 11. 装配算法与性能

当前实现会在贪心选择每加入一个候选时重新拼接并计数增长中的完整投影。最大 256 个
候选全部进入时，被重复编码的累计文本接近最终投影的 128.5 倍。

新算法为：

1. 对规范化候选文本进行一次批量编码；
2. 按现有 required、slot、score、dependency closure 规则选择；
3. 使用候选计数和有界分隔符成本形成保守初选；
4. 只渲染一次完整投影并完整计数；
5. 若超限，按最低优先级可选依赖组批量移除；
6. 每次移除后完整复核，直到满足预算；
7. required 内容本身超限时不注入 AC 投影。

机械预算不依赖单块计数可加性。BPE 在文本边界可能合并，`projection_overhead_cost`
允许为负；它只用于诊断，不再被验证为非负。

性能验收不使用不稳定的墙钟阈值作为唯一证据。单元测试注入 spy counter，验证：

- 每个候选的独立计数次数有固定上界；
- 不对每个贪心步骤重新编码完整增长前缀；
- 最终投影至少完整计数一次；
- fallback 重跑不会复用失败 profile 的任何计数；
- 工作只通过一次粗粒度 `asyncio.to_thread()` 卸载。

## 12. 最终预算不变量

对插件可见并控制的文本投影，装配器必须证明：

```math
O_{\mathrm{host}}
+ T_p(U_{\mathrm{current}})
+ T_p(F_{\mathrm{required}})
+ T_p(P_{\mathrm{AC}})
+ S
\le B_{\mathrm{input}} .
```

其中：

- `O_host` 是对 AstrBot 保留消息、角色文本、工具和其他不透明对象的有界估计；
- `U_current` 是当前输入；
- `F_required` 是不得删除的固定文本；
- `P_AC` 是 AstrContinuum 最终渲染的单一投影；
- `S` 是固定安全余量；
- `p` 是本次请求唯一 profile。

如果 required 部分已经超过预算，AstrContinuum 不裁剪用户输入、系统提示、其他插件
内容或工具 Schema；它撤销自己的请求变更，记录稳定状态并让 AstrBot 原生处理。

## 13. 故障与降级

### 13.1 原子 profile 回退

以下任一情况触发整次请求 BYTE_FALLBACK：

- `tiktoken` 不可导入；
- 编码资产缺失或 SHA-256 不匹配；
- 模型映射异常；
- 编码构造异常；
- 任一 `count_text` 或 batch count 异常；
- 计数结果不是有界非负整数。

已经由失败 profile 产生的计数、候选选择和投影全部丢弃。系统从同一不可变
`RequestView` 重新运行，不允许只替换其中一个字段的计数器。

### 13.2 其他降级

| 条件 | 行为 |
| --- | --- |
| 自动窗口不可用 | `128000`，`AUTO_SAFE_FALLBACK` |
| 手动窗口为负 | 安全兜底，`CONTEXT_LIMIT_CONFIG_INVALID` |
| 窗口不大于预留 | 不注入，`CONTEXT_LIMIT_TOO_SMALL` |
| canonical metric 缺失 | 延迟后台归约，实时请求继续 |
| metric envelope 认证失败 | 沿用存储安全锁定语义 |
| 最终 AC 投影无法满足预算 | 撤销 AC 投影，保留原生请求 |
| 后台归约输入无法满足预算 | 缩小或重排批次，不阻塞 live lane |

稳定公开代码包括：

```text
TOKENIZER_IMPORT_FAILED
TOKENIZER_ASSET_MISSING
TOKENIZER_ASSET_INVALID
TOKENIZER_MODEL_UNKNOWN
TOKENIZER_CONSTRUCTION_FAILED
TOKENIZER_COUNT_FAILED
TOKENIZER_COUNT_INVALID
TOKENIZER_BYTE_FALLBACK
CONTEXT_LIMIT_CONFIG_INVALID
CONTEXT_LIMIT_UNAVAILABLE
CONTEXT_LIMIT_TOO_SMALL
TOKEN_METRIC_MISSING
TOKEN_METRIC_CONFLICT
TOKEN_METRIC_BACKFILL_FAILED
```

代码不带模型名、Provider ID、文件路径、内容摘要或动态异常文本。

## 14. 安全与隐私

- tokenizer 完全本地执行，不发送消息、词片段、哈希或计数到网络；
- 运行时不访问 OpenAI 编码存储、models.dev 或 Hugging Face；
- 编码资产是公开只读资源，不含用户数据；
- metric 精确值位于现有 AES-GCM envelope；
- 兼容 `token_count/token_cost` 也以 AES-GCM envelope 保存，SQLite 不保留明文长度列；
- metric AAD 防止跨 artifact、跨 profile 或跨表交换；
- 请求内 block count 缓存不跨请求保留；
- tokenizer/profile 对象不得在 `repr` 中包含文本；
- 状态、日志和测试失败只输出稳定代码与有界整数；
- 不持久化原始模型字符串、Provider ID 或 tokenizer 输入；
- 临时文件、debug dump 和发布包不得包含解密文本或 tokenizer cache。

Token metric 仍可能反映内容长度，因此即使它不包含语义文本，也按受保护数据处理。

## 15. 配置与管理员可见性

`_conf_schema.json` 修改：

```json
{
  "model_context_limit": {
    "description": "模型上下文窗口（0 = 自动）",
    "hint": "默认自动读取当前会话模型的上下文窗口；填写正数时强制使用该值。自动读取失败时使用 128000，并可通过 /context_status 查看最终值和来源。",
    "obvious_hint": true,
    "type": "int",
    "default": 0
  }
}
```

`target_input_budget`、`hard_input_ceiling`、`compaction_start_ratio` 和
`provider_view_switch_ratio` 的配置语义不变。配置页不增加 tokenizer 选择器。

`/context_status` 增加全局最近状态：

```text
模型窗口：262144 · AUTO_ASTRBOT
在线计数：o200k_base · REFERENCE
持久化计数：canonical-o200k-v1
Tokenizer 降级：NONE
```

`/context_inspect` 可显示当前会话的 content-free 数值：

- context limit source；
- tokenizer mode/profile；
- BYTE_FALLBACK 次数；
- canonical metric 已补齐/待补齐 artifact 数；
- 最终受控输入预算和选中预算；
- 最近稳定 tokenizer/context code。

管理员输出不显示模型名、Provider ID、对话内容、词片段、资产路径或精确异常。

## 16. 兼容性

- Python 支持范围保持 `>=3.10`；
- AstrBot 支持范围保持 `>=4.24.0,<5.0.0`，除非真实加载矩阵证明自动窗口所需公开
  API 在下界不可用；
- 所有 AstrBot 交互只通过 `astrbot.api.*` 暴露的对象和已有 Hook 参数；
- `Context.get_using_provider`、`Provider.get_model` 和 `provider_config` 访问均为
  best-effort，缺失时安全降级；
- 旧数据库不重写任何 token 逻辑值或对象 ID；
- 旧数据库需要一次逻辑等价的加密结构迁移，将明文计数列替换为 envelope 列；
- 旧 Snapshot、Capsule 和 Journal ID 不变；
- 数据库 schema migration 重建受影响表并增加 sidecar/intent 结构，迁移后不保留
  明文计数列；
- 未安装或无法加载 `tiktoken` 时插件仍可用 BYTE_FALLBACK 启动。

## 17. 验证矩阵

### 17.1 Tokenizer 单元测试

- `o200k_base` 和 `cl100k_base` 官方固定向量；
- 中文、英文、中英混排、Emoji、组合字符、换行、JSON 和代码；
- 空文本、最大有界文本和特殊 token 字面量；
- 已知 OpenAI 模型映射；
- MiniMax、Claude、代理模型和未知模型进入 REFERENCE；
- OpenAI-compatible 非 OpenAI 模型不得误命中；
- 10% 基点倍率使用整数上取整；
- 损坏、缺失或替换的资产触发 BYTE_FALLBACK；
- 禁止任何网络访问后仍能构造编码并计数。

### 17.2 Context resolver 测试

- 正数手动配置始终优先；
- `0` 读取有效 AstrBot Provider limit；
- 缺失 Provider、字段、方法或错误类型回退 128000；
- 请求模型覆盖不匹配采用保守上限；
- 负数配置报告稳定代码；
- 小于预留的窗口不注入 AC 投影；
- 状态来源标签不泄露模型或 Provider。

### 17.3 预算与并发测试

- 随机 Unicode 候选的最终预算不变量；
- required block、工具调用/结果对和 dependency closure 不被静默拆开；
- required 内容超限时原生请求保持不变；
- 两个并发请求分别使用 OpenAI exact 和 MiniMax reference，不串 profile；
- 切换模型后历史 canonical metric 不变化；
- tokenizer 中途失败后整次 BYTE_FALLBACK 重跑；
- 256 候选的 encode 调用次数保持有界；
- BPE 边界合并导致负 overhead 时仍满足最终预算；
- `asyncio.to_thread()` 覆盖完整预算计算且不逐 count 调度线程。

### 17.4 存储与迁移测试

- 新 artifact 与 canonical metric 正常原子提交；
- 明文兼容计数结构迁移保持所有解密值、ID、关系和幂等行为；
- 结构迁移中断、回滚和 post-commit scrub 恢复均保持 locked/no-write；
- canonical 故障时权威 Journal 仍可提交且产生 backfill intent；
- 旧 fixture 的解密 token 值和对象 ID 完全不变；
- 渐进补齐可中断、重启和重复执行；
- metric CAS 冲突停止使用错误派生值；
- 错误密钥、错误 AAD、跨行交换和篡改 tag 全部认证失败；
- 原始 SQLite、WAL、备份和发布包扫描不到 synthetic 兼容计数或 metric 明文；
- 加密轮换后 metric 仍可认证并保持相同逻辑值。

## 18. 实现顺序约束

后续实现计划必须按以下依赖顺序拆分，具体文件和测试由 implementation plan 确定：

1. profile、registry、离线资产校验与固定向量；
2. router 与 context resolver；
3. 加密 Token metric sidecar 和迁移；
4. request-scoped counter 注入；
5. 实时装配复杂度改造与最终预算复核；
6. 后台归约 profile 与 canonical metric；
7. 配置、状态和双语文档；
8. Python/AstrBot/离线/包体验证；
9. PR 审阅、合并后再创建 `v0.2.1` tag 和 Release。

每一步先写失败测试，再写最小实现。不得在 tokenizer 尚未通过固定向量和离线测试时
切换生产默认计数；不得在 sidecar 迁移尚未验证时让 segmenter 使用 canonical metric。

## 19. 验收标准

本设计完成实现的判定条件为：

1. `model_context_limit = 0` 能在真实 AstrBot 请求中得到正数有效窗口，并能显示来源；
2. 中文、Emoji 和混排文本不再按 UTF-8 字节作为正常在线预算；
3. 已知 OpenAI 模型、MiniMax/Claude 未知模型和 byte fallback 三条路径均可观测；
4. 任何请求只使用一个 request profile，模型并发和切换不混算；
5. Journal/Snapshot/Capsule 的既有不可变与幂等语义保持；
6. 旧数据库可渐进获得 canonical metric，兼容 token 字段的逻辑值和对象 ID 不变；
7. 最终 AC 投影在注入前通过完整 request-profile 预算复核；
8. tokenizer、资产、元数据、metric 或线程任务故障不阻断原生 AstrBot 聊天；
9. 运行时无 tokenizer 网络访问，metric 与内容不以明文进入 SQLite、WAL、日志或包；
10. Python 3.10–3.13、Windows 3.12、真实 AstrBot 探针和 `<16 MiB` 发布门禁全部通过。
