# AstrContinuum v0.2.0 Sparse Context Engine Design

Status: approved implementation direction

Date: 2026-07-27

Target: `astrbot_plugin_astrcontinuum` release `v0.2.0`

## 1. Goal

AstrContinuum v0.2.0 replaces fixed-priority context selection with a bounded sparse
dependency-graph engine. The engine combines:

- exact structured records produced by the background compiler;
- the committed Snapshot and its Capsule memberships;
- the contiguous uncommitted Journal Delta;
- the current user request;
- explicit hard-inclusion and dependency constraints.

For each projected request, it constructs one sparse graph, computes query-conditioned
activation, selects content inside the exact request budget, estimates the error introduced by
state reduction, and selectively restores source blocks until the result is verified or the safe
fallback takes over.

The release contract is:

```text
authoritative Journal is never rewritten
small-model output is never trusted as free-form context
hard constraints and provenance are never optional
graph or solver failure never blocks native AstrBot processing
unverified graph output never replaces the deterministic fallback
```

Both background and live paths use the same graph construction, constraint, reduction, and
certificate code. Background work verifies that a candidate Snapshot is graph-valid before
publication. The live path combines that Snapshot with its current Delta and current request in
one request-local computation.

## 2. Public Terminology

Code, configuration, documentation, commands, logs, commits, and release notes use
computer-science and numerical-computing terminology only.

| Concept | Public name |
| --- | --- |
| durable source of truth | authoritative Journal |
| structured graph item | context coordinate |
| typed relationship | sparse relation |
| matrix generated by relationships | propagation operator |
| required inclusion/equality | constraint row |
| query-dependent input | query activation |
| eliminating query-independent internal state | state reduction |
| restoring omitted source blocks | adaptive recovery |
| proof that one result is safe to use | error certificate |
| discontinuous correction or lifecycle change | hard state transition |

The implementation must not introduce domain-specific analogies into public names. Standard
terms such as sparse matrix, graph Laplacian, Schur complement, KKT system, conjugate gradient,
constraint projection, and residual are allowed because they are established numerical-computing
terms.

## 3. Authority and Data Boundaries

### 3.1 Authoritative state

The following existing records remain authoritative:

- immutable Journal events and their deterministic sequence;
- committed Capsules with exact source-event provenance;
- committed Snapshots and Snapshot/Capsule memberships;
- the active Snapshot pointer and durable compaction job state.

The graph engine never deletes, rewrites, or reorders them.

### 3.2 Derived state

The sparse graph, propagation operator, reduced operator, query activation, solver state, and
error certificate are request-local or background-candidate-derived data. In v0.2.0 they are
reconstructed from encrypted durable domain records and are not persisted as a second
conversation store.

This choice:

- avoids a new plaintext or correlation-bearing durable index;
- avoids cache invalidation and a second authority;
- makes restart behavior deterministic;
- keeps encryption, rotation, migration, and backup behavior unchanged;
- permits later persistence only after a separate encrypted-format design.

No decrypted content graph is stored in a process-global cache.

## 4. Sparse Graph Model

### 4.1 Context coordinates

Every candidate block becomes one stable context coordinate. Coordinate kinds are:

- active goal;
- hard constraint;
- raw Journal event;
- exact anchor;
- active task;
- decision;
- entity;
- dependency;
- episode background;
- global background.

A coordinate contains:

```text
coordinate id
candidate block id
kind and runtime slot
source event ids
Capsule id or raw event sequence
required flag
bounded token cost
content-free structural attributes
```

The coordinate's text remains in the existing request-local `CandidateBlock`; matrix types do
not duplicate it and must keep content fields out of `repr`.

The numerical activation value answers only:

```text
How strongly is this coordinate connected to the current request and required context?
```

It does not represent factual truth, user intent correctness, or the probability that the language
model will obey the included text.

### 4.2 Sparse relations

Relations are deterministic and typed. v0.2.0 permits:

- shared exact source-event provenance;
- common Capsule membership;
- explicit Capsule dependency target;
- entity or decision identifier linkage;
- contiguous raw-event order;
- tool-call/tool-result pairing;
- required-block companion linkage;
- current-query exact lexical activation.

The small model may propose structured Capsule fields, but it cannot provide arbitrary matrix
entries or weights. Existing extractive validation must first prove exact source spans, speaker
ownership, closed schema, deterministic ids, and source coverage.

Each relation type has a fixed bounded base weight. Long multi-coordinate relations are normalized
so they cannot dominate solely because they contain more endpoints.

### 4.3 Propagation operator

Let `R` be the implicit sparse relation matrix and `W` the bounded diagonal relation-weight
matrix. The engine constructs:

```math
Q = R^\mathsf{T} W R + D + \varepsilon I
```

where:

- `D` is a positive diagonal stability and priority term;
- `epsilon` is a fixed positive regularizer;
- `Q` is symmetric positive definite after valid constraint projection;
- the implementation never forms an explicit inverse.

`R` and `Q` are represented with bounded sparse adjacency structures. Dense storage is allowed
only for small local blocks during state reduction and tests.

## 5. Constraint Matrix

### 5.1 Scope

The sparse constraint matrix `C` controls numerical activation and reduction eligibility. It
does not encode natural-language truth.

Supported equality rows are:

```text
a[j] = 1                 required coordinate remains active
a[j] = 0                 structurally inactive coordinate remains suppressed
a[i] - a[j] = 0          inseparable coordinates share activation
```

Final text packing separately enforces hard inclusion and dependency closure. A numerical
constraint passing is not accepted as proof that a required text block was packed.

### 5.2 Constrained solve

For query activation vector `q`, the canonical problem is:

```math
\min_a \frac{1}{2} a^\mathsf{T} Q a - q^\mathsf{T} a
\quad \text{subject to} \quad C a = d
```

with KKT form:

```math
\begin{bmatrix}
Q & C^\mathsf{T} \\
C & 0
\end{bmatrix}
\begin{bmatrix}
a \\
\lambda
\end{bmatrix}
=
\begin{bmatrix}
q \\
d
\end{bmatrix}.
```

v0.2.0 compiles the closed constraint-row forms into exact coordinate fixing and equivalence
classes before solving. This preserves sparsity and avoids a general indefinite solver in the live
path. Invalid or contradictory rows fail with a stable content-free code.

### 5.3 Constraint-aware state reduction

Every coordinate referenced by an active constraint is promoted to the retained set. Therefore,
after partitioning activation into retained `a_r` and eliminable `a_e`:

```math
C = [C_r \quad 0].
```

The reduced problem is:

```math
\bar Q = Q_{rr} - Q_{re} Q_{ee}^{-1} Q_{er}
```

```math
\bar q = q_r - Q_{re} Q_{ee}^{-1} q_e
```

```math
\begin{bmatrix}
\bar Q & C_r^\mathsf{T} \\
C_r & 0
\end{bmatrix}
\begin{bmatrix}
a_r \\
\lambda
\end{bmatrix}
=
\begin{bmatrix}
\bar q \\
d
\end{bmatrix}.
```

`Q_ee^-1` denotes linear solves, never an explicitly constructed inverse. If a proposed reduction
would leave any nonzero constraint support in the eliminated set, reduction is rejected rather
than silently weakening the constraint.

## 6. Background Candidate Verification

The compiler continues to use closed, extractive, exact-source output. It must not request or
accept a narrative retelling.

After existing permanent validation and before a candidate can become `READY_TO_COMMIT`, the
background path:

1. converts candidate Capsules into bounded candidate blocks;
2. constructs the same sparse graph used by the live engine;
3. promotes all required and constraint-supported coordinates;
4. reduces only query-independent internal coordinates;
5. runs fixed synthetic probe activations for goals, constraints, tasks, anchors, decisions,
   dependencies, entities, and recent-event linkage;
6. reconstructs eliminated activation and computes an error certificate;
7. rejects publication if constraints, provenance, convergence, or probe equivalence fail.

The committed Snapshot remains the existing Capsule bundle and exact rendered structured context.
The derived matrix is rebuilt when needed; the successful graph certificate contributes to the
Snapshot's existing mechanical validation outcome without adding sensitive durable fields.

A failed graph candidate follows the existing durable retry path. It cannot affect the active
Snapshot or live request.

## 7. Live Query Activation

### 7.1 One-stage request view

For every projected request, the engine receives exactly one validated `RequestView` containing:

- one committed Snapshot and its ordered Capsule memberships, or the empty base;
- one contiguous Journal Delta through the request high-water mark;
- the current input outside the historical projection;
- the complete bounded set of candidate blocks.

The Snapshot, Delta, and current query are processed by one engine call. Query activation is not
computed against an earlier Snapshot and reused after the view changes.

### 7.2 Activation sources

The query vector is assembled from:

- exact normalized lexical overlap;
- candidate kind and runtime-slot priors;
- explicit identifiers and dependency targets;
- exact source-event linkage;
- required-coordinate activation;
- recency only for raw Delta ordering.

No embedding service or extra provider call is required in v0.2.0. The configured small model is
used only by background extractive compilation.

### 7.3 Sparse solve

The live solver:

1. compiles equality constraints into coordinate groups;
2. applies prescribed group values exactly;
3. solves the remaining symmetric positive-definite system with bounded preconditioned conjugate
   gradient;
4. checks finite values, convergence, iteration limit, and normalized residual;
5. reconstructs coordinate activations;
6. sorts optional candidates by verified activation per token cost while preserving runtime-slot
   safety order.

Required blocks are reserved before optional ranking.

## 8. Error Certificate and Adaptive Recovery

The certificate contains only content-free values:

```text
engine mode
coordinate, relation, retained, and reduced counts
solver iteration count and convergence code
normalized stationarity residual
constraint residual
reconstruction residual
provenance coverage
required-block coverage
adaptive-recovery pass count
input and selected budget units
```

The corrected residuals are:

```math
r_a = q - Q a - C^\mathsf{T}\lambda
```

```math
r_c = d - C a.
```

The implementation also compares the reduced result with local unreduced relation blocks. A
coordinate group with high local error receives an error-per-token priority. The engine restores
the highest-priority omitted group, rebuilds the affected request-local graph, and retries within
fixed pass and time bounds.

The engine reports:

- `VERIFIED`: all certificate gates pass without restoration;
- `REFINED`: restoration was required and all gates then pass;
- `DEGRADED_RAW`: the deterministic fallback was used;
- `UNVERIFIED`: Shadow computation completed but did not qualify for use.

If the hard budget is reached before verification, the engine retains all hard constraints,
current active tasks, exact anchors, complete tool pairs, and the longest contiguous recent raw
suffix that fits. It never labels this emergency result as verified reduction.

## 9. Runtime Modes

The user-facing mode is:

- `active`: graph output may replace legacy fixed-priority output only when verified;
- `shadow`: graph output and metrics are computed, but the legacy output is sent;
- `off`: the graph engine is not run.

`DEGRADED_RAW` is an observed request status, not a configured mode.

The v0.2.0 default is `active`. This is safe because any exception, non-convergence, certificate
failure, missing required block, or budget inconsistency selects the existing deterministic
fallback for that request.

Shadow mode must compare both paths from the same immutable `RequestView`. It must never perform
a second Journal read that could make the comparison cross two different high-water marks.

## 10. Triggering

Graph work follows context pressure, not a fixed conversation-round count.

Existing pressure decisions remain authoritative:

- below the compaction threshold: native AstrBot history remains unchanged;
- above the compaction threshold: durable background intent is raised;
- above the projection threshold: a bounded AstrContinuum provider view is assembled.

The engine runs only when a provider projection is required, except for background candidate
verification. It is not added to every short request.

## 11. Small-Model Boundary

The background model receives deterministic event segments and a closed extractive schema. It may
select:

- exact source spans;
- structured goal, constraint, decision, progress, open-loop, preference, entity, dependency,
  emotional-context, and anchor categories;
- a bounded confidence value.

The program:

- derives all ids;
- proves every span is exact source text from the declared event;
- verifies speaker ownership and source coverage;
- maps structured fields to graph coordinates;
- supplies all relation weights and constraints;
- rejects unknown fields, prose, paraphrases, and unsupported source references.

Model confidence is clipped and may only weaken an optional relation. It cannot create a required
constraint or override Journal status.

## 12. Security and Privacy

The storage-security design remains authoritative.

Additional graph requirements are:

- no content, entity name, source span, SessionKey, provider id, key path, ciphertext, or object
  representation in graph logs or certificate output;
- matrix and graph types keep content-bearing objects out of `repr`;
- no plaintext graph dump, debug export, temporary file, or global cache;
- authentication failure locks storage and bypasses graph work;
- graph errors expose only stable codes;
- `/context_status` remains a global operational overview;
- `/context_inspect` remains current-session scoped with a full SessionKey recheck after queries.

## 13. Administrator Visibility

`/context_status` adds:

```text
上下文引擎：ACTIVE | SHADOW | OFF
最近引擎状态：VERIFIED | REFINED | DEGRADED_RAW | UNVERIFIED | NONE
```

`/context_inspect` adds current-session, content-free metrics:

- original candidate count and selected count;
- relation, constraint, retained, and reduced counts;
- selected budget units and reduction ratio;
- normalized residual band;
- recovery pass count;
- required and provenance coverage;
- small-model structured candidates accepted and rejected when available;
- last stable engine code.

No floating-point value needs more than a bounded scientific-notation representation. NaN and
infinity are never rendered.

## 14. Verification Matrix

The exact same synthetic Journal fixture is evaluated through:

- the existing deterministic fixed-priority path;
- the sparse graph path in Shadow mode;
- the sparse graph path in Active mode.

Predeclared factors include:

| Factor | Levels |
| --- | --- |
| context pressure | 70%, 85%, 95%, above hard ceiling |
| language | Chinese, English, mixed |
| extraction quality | deterministic, valid small-model, injected invalid relations |
| state transition | ordinary, correction, retraction, reopened task, tool failure, persona change |
| relation structure | complete, cross-link removal, delayed Snapshot |
| worker state | current, stale, retry, unavailable |
| storage state | active, missing key, wrong key, modified ciphertext |

Primary gates:

- zero hard-constraint omission;
- zero speaker/persona attribution mismatch in exact probes;
- complete required tool-call/tool-result pairs;
- complete provenance for every selected block;
- exact downstream probe agreement with the full authoritative fixture;
- deterministic fallback on injected graph and solver faults;
- no secret or fixture content in metrics, logs, or archive;
- no regression in native AstrBot request completion.

Performance gates on the reference workload:

- at least 35% projection reduction at equal primary-gate correctness;
- p95 graph-engine time no greater than 50 ms for the configured maximum candidate count;
- graph-engine time no greater than 5% of the measured provider request duration in integration
  diagnostics;
- bounded memory proportional to coordinates plus relations;
- NumPy is the required native numerical baseline and is imported lazily only when the engine
  runs;
- SciPy is an optional sparse accelerator and is never required for plugin initialization;
- the plugin archive contains no vendored wheel or third-party binary;
- a bounded pure-Python reference backend remains available for tiny validation and deterministic
  backend-failure tests.

## 15. Error Model

Stable codes include:

```text
GRAPH_INPUT_INVALID
GRAPH_LIMIT_EXCEEDED
GRAPH_RELATION_INVALID
GRAPH_WEIGHT_INVALID
GRAPH_CONSTRAINT_INVALID
GRAPH_CONSTRAINT_CONFLICT
GRAPH_REDUCTION_INVALID
GRAPH_OPERATOR_INVALID
GRAPH_SOLVER_NOT_CONVERGED
GRAPH_NUMERIC_INVALID
GRAPH_CERTIFICATE_FAILED
GRAPH_REQUIRED_BLOCK_MISSING
GRAPH_PROVENANCE_INCOMPLETE
GRAPH_ADAPTIVE_LIMIT
```

Codes have no dynamic or content-bearing suffix. Active mode handles every graph code by using
the deterministic fallback. Background verification handles every graph code by rejecting the
candidate Snapshot through the existing durable retry state machine.

## 16. v0.2.0 Release Gate

The sparse context engine is part of v0.2.0, not deferred to a later release.

v0.2.0 is ready for user review only when:

1. remaining storage/lifecycle audit findings are fixed;
2. background candidate graph verification and live query activation use the same engine;
3. `C` participates in retained-set selection, solving, residual checks, and pack validation;
4. Shadow and Active modes are covered by real request-view tests;
5. all error-certificate and adaptive-recovery gates pass;
6. the complete falsification matrix passes;
7. Ruff, mypy, full pytest, AstrBot validation, package whitelist, archive-size, and plaintext
   scans pass on the exact source to be packaged;
8. version, metadata, configuration, README, architecture, security, evaluation, and changelog
   agree on v0.2.0;
9. all commits are authored and committed as the repository owner's configured identity;
10. the final branch is presented for review before any remote push or pull request.
